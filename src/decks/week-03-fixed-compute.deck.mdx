# Scale is an allocation problem

With one GPU-day, would you spend it on a **larger model**, **more distinct
tokens**, or **more updates over the same data**?

```notes
Open by collecting a silent initial choice — a show of hands or a poll, not a
discussion yet. The rest of the deck returns to this question at the exit
ticket.
```

## Project 1 has three coupled quantities

- **N** — learned parameters
- **D** — training tokens processed
- **C** — training compute

| Constraint | Value |
| --- | --- |
| Design target | 32M learned parameters |
| Absolute eligibility boundary | 33.6M learned parameters (5% tolerance) |
| Compute allowance | 24 T4-equivalent hours |
| Training FLOP ceiling | 4.0×10¹⁷ |

**Takeaway:** every proposed run must fit *all* of these at once — a plan that
saves parameters but blows the FLOP ceiling is not a legal plan.

## Bigger is not automatically better

Three ways a plan can fail without touching the parameter boundary:

1. too many parameters for the data on hand — capacity the corpus can't fill
2. many repeated passes over a narrow corpus — compute spent, little new
   information gained
3. a tiny model trained long after useful validation improvement stopped —
   time spent past the point of return

**Discuss:** for each sketch, which resource — model, data, or compute — is
actually the bottleneck?

## Kaplan et al.: smooth scale relationships

- reported smooth relationships between loss and N, D, C across many orders
  of magnitude
- larger models are more *sample-efficient* — they reach a given loss with
  fewer tokens
- weak sensitivity to architectural shape within the studied range
- early stopping is compute-optimal: stop before full convergence on a fixed
  budget

**Callout:** the studied regimes are far above 32M. Read this as evidence of
a shape, not a recipe for this course's model.

```notes
Cite: Kaplan et al., "Scaling Laws for Neural Language Models"
(arxiv.org/abs/2001.08361). No figure from the paper is reproduced here —
see the deck's figure/source register slide for the full citation.
```

## Chinchilla changed the allocation

| Question | Earlier view (Kaplan-era) | Chinchilla-era view |
| --- | --- | --- |
| Under fixed compute, favour... | more parameters | parameters and tokens roughly together |
| Main risk | — | undertrained large models |

## A token is not a unit of value

| Source | Quality signal |
| --- | --- |
| Clean, diverse stories | high value per token |
| Duplicated stories | diminishing value with repetition |
| OCR noise | actively harmful |
| Synthetic textbook-like stories | can raise value per token, not guaranteed |

Quality, diversity, duplication, provenance, and domain fit all change what a
token is worth.

```notes
TinyStories/Phi are evidence that data design can change small-model
outcomes — not proof that synthetic data is always superior. Cite: Eldan and
Li, "TinyStories" (arxiv.org/abs/2305.07759); Gunasekar et al., "Textbooks Are
All You Need" (arxiv.org/abs/2306.11644).
```

---

## Count data twice

Two ledgers, not one:

1. **unique source/token inventory** — how much distinct material exists
2. **tokens processed during optimisation** — how much the optimiser actually
   saw, including repeats

Multiple epochs increase the second without increasing the first — a report
needs both numbers, or a duplication claim can't be checked.

---

## From batch to compute

- **sequence length** × **sequences per micro-batch** × **gradient
  accumulation** → effective tokens per update
- **updates** × **effective tokens per update** → total tokens processed

The repository is canonical for hardware conversion and FLOP estimation — the
ledger relationship above is for reasoning about a plan, not for computing a
number to report without running the tool.

Early instability calls for a short warm-up; later refinement calls for
decay. An aggressive rate late in training can destroy a useful checkpoint —
a lesson that carries forward directly into Projects 2 and 3's post-training
stages.

## Stability signals

| Signal | Warning pattern | Ambiguous pattern |
| --- | --- | --- |
| Train/validation loss | validation rises while train falls | validation flattens early |
| Gradient norm | sudden spike or divergence | one isolated spike |
| Throughput/memory | steadily degrading throughput | one slow step |
| Fixed-prompt samples | repeated or degenerate text | one attractive sample |

A single spike, or one attractive sample, is not a conclusion on its own.

---

## A pilot answers one uncertainty

**Template:** hypothesis → one changed factor → controlled variables →
maximum spend → measurement window → stop rule → decision the result can
change.

Contrast this with an undirected hyperparameter sweep, which spends budget
without naming what it will decide.

## Decision 2: continue, revise, or stop?

A fictional pilot: training loss falls, validation loss flattens, gradient
norm is stable, projected runtime is 30 hours, samples repeat source phrases.

**Choose an action, and name the evidence for it.**

```notes
Reveal after discussion: several defensible actions exist here (continue
briefly to confirm the flattening, revise the data mixture to address
repetition, or stop and reallocate) — provided the next check is made
explicit before acting.
```
